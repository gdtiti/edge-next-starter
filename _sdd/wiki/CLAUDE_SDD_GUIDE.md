# Claude 环境下的 SDD 范式实现指南

## 🎯 概述

本指南详细说明如何在 Claude 环境中基于现有的 `.claude/commands/SDD` 架构扩展新的代理和命令，实现可扩展的 SDD (规范驱动开发) 范式。

## 🏗️ Claude SDD 架构基础

### 当前架构概览
Claude SDD 系统基于 `.claude/commands/SDD/` 目录构建，采用���块化设计：

```
.claude/commands/SDD/
├── README.md                    # 系统说明文档
├── agents/                      # SDD 专业代理
│   ├── init-architect.md        # 初始化架构师
│   ├── planner.md               # 规划专家
│   ├── implementer.md           # 实现专家
│   ├── analyzer.md              # 分析专家
│   ├── debugger.md              # 调试专家
│   └── learner.md               # 学习专家
├── tasks/                       # 可执行任务
├── templates/                   # 文档模板
├── data/                        # 数据和配置
└── checklists/                  # 质量检查清单
```

### 核心组件
- **SDD 编排器** (`/sdd`) - 统一入口和工作流协调
- **专业代理** - 领域专家，各司其职
- **可执行任务** - 具体的工作流程
- **模板系统** - 标准化文档生成

- **工作原则**: [核心工作原则]

## 主要能力

2. **[能力2]**: [详细描述]
3. **[能力3]**: [详细描述]

## 核心命令
- `*[command1]` - [命令描述]
- `*[command2]` - [命令描述]

## 工作流程

#### 2. 创建新代理示例

**示例：测试专家代理**

```markdown
# 测试专家 - 测试卫士 🧪

## 角色定义
- **专长领域**: 软件测试、质量保证、自动化测试
- **核心职责**: 设计测试策略、执行测试、质量保证
- **工作原则**: 测试驱动、质量第一、全面覆盖

## 主要能力
1. **测试策略设计**: 根据功能需求设计全面的测试策略
2. **自动化测试**: 创建和维护自动化测试套件
3. **性能测试**: 执行性能测试和压力测试
4. **质量分析**: 分析测试结果和代码质量指标

## 核心命令
- `*test-strategy` - 设计测试策略
- `*test-automation` - 创建自动化测试
- `*performance-test` - 执行性能测试
- `*quality-report` - 生成质量报告

## 工作流程
1. 分析功能需求和验收标准
2. 设计测试策略和测试用例
3. 创建自动化测试脚本
4. 执行测试并分析结果
5. 生成质量报告和改进建议

## 质量标准
- 测试覆盖率 > 80%
- 自动化测试通过率 100%
- 性能测试达到预期指标
- 质量报告完整准确

## 使用示例
/sdd
*agent tester
*task test-strategy --feature "用户登录模块"
```

## 🧠 Claude-SDD 错误处理详解

### 针对四大问题的解决方案

#### 1. 防止急于解决错误

```markdown
请严格按照 SDD 错误处理流程：

**强制要求**：
- 必须先完成根因分析，不允许直接跳到解决方案
- 使用 5 Whys 方法连续追问至少5个为什么
- 从多个角度分析问题（技术、流程、人员、环境）

**示例分析**：
问题：数据库查询超时
1. 为什么超时？→ 连接池耗尽
2. 为什么连接池耗尽？→ 查询未正确关闭连接  
3. 为什么未正确关闭？→ 异常处理不完善
4. 为什么异常处理不完善？→ 缺乏统一的异常处理规范
5. 为什么缺乏规范？→ 项目初期未制定详细的数据库操作规范
```

#### 2. 防止重复设计

```markdown
请设计解决方案前先检查历史：

**历史检查要求**：
- 检查项目中是否已有类似功能
- 查找之前是否尝试过类似解决方案
- 分析历史方案的成功/失败原因

**防重复机制**：
如果发现历史失败方案：
⚠️ 该方案已于 [日期] 尝试失败
失败原因：[具体原因]
建议：考虑其他方案或解决导致失败的根本问题
```

#### 3. 防止过度简化

```markdown
请设计完整的解决方案：

**方案要求**：
- 必须提供至少3个不同方案供对比
- 禁止使用模拟数据作为最终验证
- 必须考虑方案对现有系统的影响
- 必须有完整的验证计划

**验证要求**：
- 单元测试覆盖率 > 80%
- 集成测试通过
- 性能影响 < 5%
- 无安全风险
```

#### 4. 防止遗忘教训

```markdown
请建立知识库记录：

**记录要求**：
- 详细记录每个错误的分析过程
- 记录所有尝试过的方案和结果
- 提取可复用的经验和模式
- 更新相关的开发指南

**学习机制**：
- 定期回顾历史错误模式
- 更新最佳实践文档
- 制定预防措施
```
