## 用户输入

```text
$ARGUMENTS
```

你必须考虑用户输入后再继续（如果不为空）。

## 概述

分析命令检查所有文档间的一致性和完整性，确保规范、计划、任务之间没有冲突或遗漏。这个命令会：

1. **一致性检查**：验证文档间的信息一致性
2. **完整性检查**：确保所有必要信息都已定义
3. **覆盖度分析**：检查需求到实现的覆盖情况
4. **质量评估**：评估整体文档质量

## 执行流程

### 1. 文档收集
收集以下文档：
- **项目宪法**：`_sdd/memory/constitution.md`
- **功能规范**：`_sdd/specs/[feature-name]/spec.md`
- **技术计划**：`plan.md`
- **任务清单**：`tasks.md`
- **数据模型**：`data-model.md`
- **API 契约**：`contracts/`

### 2. 一致性检查

#### 规范 ↔ 计划一致性
- [ ] 功能需求都有对应的技术方案
- [ ] 性能要求在技术计划中得到体现
- [ ] 安全要求在技术计划中得到落实
- [ ] 用户故事都有对应的实现方案

#### 计划 ↔ 任务一致性
- [ ] 技术组件都有对应的实现任务
- [ ] API 端点都有对应的开发任务
- [ ] 数据模型都有对应的创建任务
- [ ] 架构决策都有对应的实现步骤

#### 任务 ↔ 规范覆盖度
- [ ] 每个用户故事都有对应的任务
- [ ] 每个功能需求都有对应的实现
- [ ] 每个验收标准都有对应的验证
- [ ] 每个成功指标都有对应的测量

### 3. 完整性检查

#### 需求完整性
- [ ] 用户故事要素完整（角色、目标、价值）
- [ ] 验收标准具体可测试
- [ ] 边界条件明确定义
- [ ] 异常处理考虑周全

#### 设计完整性
- [ ] 数据模型关系清晰
- [ ] API 接口定义完整
- [ ] 安全方案全面覆盖
- [ ] 性能优化措施到位

#### 实现完整性
- [ ] 任务分解粒度适中
- [ ] 依赖关系明确
- [ ] 时间估算合理
- [ ] 质量检查点设置

### 4. 质量评估

#### 文档质量指标
- **清晰度**：表述是否清晰明确
- **完整性**：信息是否完整齐全
- **一致性**：文档间是否一致
- **可执行性**：是否足以指导实现

#### 评分标准
- **优秀 (90-100分)**：文档质量极高，可直接用于实现
- **良好 (80-89分)**：文档质量较好，少量修改后可用
- **一般 (70-79分)**：文档质量一般，需要较多修改
- **较差 (60-69分)**：文档质量较差，需要大幅修改
- **不合格 (<60分)**：文档质量太差，不建议用于实现
